# Применение минимального уровня проекта

Читай при `NEEDS_APPLICATION` или `APPLICATION_UNPROVEN` от `kb_apply.py`.
Версия установленного скилла — `metadata.version`; минимальный уровень проекта
задаёт `metadata.minimum_project_version`, сейчас `7.2.0`. Маркер проекта
`kb_standard_version` меняют последним. Совместимый выпуск выше уже принятого
минимума не открывает миграцию заново.

## `application_cycle` — порядок перехода

Выполни `kb_apply.py <root>`. Применяется только ещё не принятая дельта,
а не весь стандарт заново. Если владелец задал более ранний target, используй
`--target-version` и не расширяй поручение. Исторический `contract_line`
не является второй текущей версией.

1. Начни с чтения: `kb_skills.py <root> --prepare-candidate`. Принятое `action: none`
   не требует нового кандидата. До первой записи сохрани точный pre-change commit
   и адрес файла, откуда прочитан marker. Разбери незакоммиченное с его владельцем.
   Для tracked-only изменения commit уже даёт откат; второй checkout не нужен.
2. Примени относящиеся блоки ниже. Не переделывай работающую структуру, неизменные
   методы, связи и действительные доказательства ради номера версии.
3. Выполни только проверки, влияющие на решение. При изменении роли используй
   цикл `project-roles.md` → `role_acceptance`, включая проектный validator
   и обычный вопрос из свежего контекста. Не записывай успех заранее. Исправление
   validator требует `PENDING`, новых связанных входов и одного нового запуска.
4. Покажи содержательный diff, реальные `PASS`, `FAIL`, `UNKNOWN`, цену,
   открытые вопросы и откат. Если ветка продвинулась, проверь промежуточные commits
   и до финализации замени `source.commit` квитанции на фактический parent
   кандидата: прежний снимок сессии не откатывает безопасно всю новую работу. Внешнее состояние проходит собственное поэтапное
   переключение с проверкой, а не откат только Git.
5. После принятия показанного результата запиши квитанцию, затем поставь marker
   минимального уровня. Выполни точечный commit и разрешённый push.

Обычная команда начать миграцию не означает приёмку ещё не показанного результата.
Владелец может явно делегировать автономную проверку, приёмку и раскатку.
Тогда укажи исполнителя и основание делегирования в `accepted_by`, а личное
непроведённое ревью владельца оставь открытым. Уже предоставленные полномочия
не требуют повторного вопроса. Предметная корректность обсуждается столько,
сколько нужно; служебная финализация не подменяет эту работу.

## `below_7` — проекты ниже 7.0

Сохрани предметную структуру и унифицируй текущий вход в NOW по
`knowledge-routing.md`. Проверь адреса знаний и разрешённые сводные, различая
области, методы и инструменты. Добавь новые виды targets или наследование роли
только при реальной потребности. Координатор не заменяет специалиста.

Примени проверяемое основание выводов по `retrieval.md`; принятый SQL или ledger
не дублируют текстовой квитанцией. Для входящих сохрани полный объявленный
комплект, атрибуцию, извлечение, неизвестное и продолжение по `incoming.md`.
Проверь распространение исправлений. Существующая предметная БД остаётся каноном.

Убери дубли старой приёмки: процедура роли принадлежит `project-roles.md`,
применение уровня — этому файлу. Сначала безопасный сценарий чтения или
временная копия, затем затронутые проверки и реальная оценка пользы. Исход
«уже выполняется» подтверждается ссылкой. После этого применяются следующие
две дельты; принятый уровень 7.0 этот блок пропускает.

## `7_0_to_7_1` — стоимость и приёмка

Проверь стоимость выбранных условий и ролей: физический файл один раз,
раздел с подразделами, для query — рецепт. Все роли вместе являются отдельным
верхним сценарием. Разные selectors могут делить метод без создания профессий.
Проверь область бюджета, единицы, обоснование и запас. При превышении сначала
устрани ненужный выбор и дубли; смысловое разделение требует доказанной пользы.
Если нужный маршрут дороже, обоснуй бюджет. Полный вход и незавершённое не теряются.

Сними относящиеся требования выдумывать `valid_until`, создавать четыре
отдельных файла приёмки или повторять миграцию после каждого patch. Вместо
выдуманного срока используй источник, наблюдение и неизвестность свежести.
Переиспользуй неизменные доказательства. На затронутом маршруте проверь
обычный, составной и конфликтный вопрос; сравни ответ и цену. Для неизменного
покажи «уже выполняется» с основанием.

`COST_SCOPE_PARTIAL` означает неучтённые условные зависимости: включи нужное
в `route_files` либо назови неполный охват. Статический результат не измеряет
весь контекст и фактические токены. Принятую дельту 7.1 не повторяют.

## `7_1_to_7_2` — дороги к знанию

Запусти `kb_index.py <root> --coverage`. При ином корне знания объяви его
в правилах; `NOT_CHECKED` не является успехом. Недостижимым файлам дай маршрут
из индекса и соответствующей роли либо ссылку от входа области. Намеренные
исключения объяви и оставь видимыми, без пофайловых маршрутов ради счётчика.

Запусти `kb_check.py <root>`. У производного результата исправь неустойчивый
`generated_from` на tracked источник, рецепт или именованный внешний канон.
Выданные людям численные отчёты должны иметь методику показателей в базе.
Повтори coverage и один вопрос, на котором прежде пропускался существующий факт:
роль должна дойти до него по своим маршрутам. Принятую дельту 7.2 не повторяют.

## `release_actions` — действия без смены marker

Совместимый выпуск может требовать настройки без нового уровня проекта.
Читай `PROJECT_RELEASE_ACTIONS` из `kb_apply.py` и выполняй только непринятое.
В выводе `kb_apply.py` пометка `⟦Д: …⟧` — обязательное дело: прежнее соглашение
проекта стало неверным или неполным. Пометка `⟦В: …⟧` — новая возможность;
каждая применимая получает исход владельца: принято, отклонено или отложено,
с причиной и условием возврата в правилах проекта.
При нескольких ролях объяви подходящий `entry_role` либо выбирай роль задачи
при входе; допустимое отсутствие роли объясни. Собственный старый hook снимают
после работы общего. Инструкции входа следуют `service-layer.md` → `entry`;
доставка версии и разбор долгов — его разделу `update`.

Начальное чтение установленного entry в правилах можно исправить точечно без
нового marker или повторной приёмки неизменных ролей. Проверь реальную новую
задачу: текст инструкции сам не является подтверждением её исполнения.

## `receipt` — короткая квитанция

`KB_RELEASE_APPLICATION.json` schema 3 хранит один текущий переход:
`from_version`, `to_version`, `status`, исходный commit и `version_source`,
решение с `accepted_by` и `accepted_at`, `finalized_at` и открытое.
Для нового проекта `from_version: null`, а source commit — тот, где marker
появился впервые. Используй незаполненный шаблон `assets/templates/release-application.json`;
неизвестные результаты не превращай в готовые статусы.

Старые schema 2 с `from_line` и `to_line` остаются читаемыми без косметического
перехода. История квитанций и откат живут в Git; второй набор release rows,
хешей, адресов evidence и одинаковых owner gates не нужен. Открытый вопрос
не блокирует структурную приёмку, если уполномоченный принял безопасный режим.

Полный набор тестов самого скилла, повтор живого теста при неизменных байтах
и связях, mutation suite и несвязанное предметное исследование не являются
обязательной ценой обычного перехода. Они нужны при соответствующем риске
или специальном аудите. Отсутствие проверки не доказывает её результат.
