# Сервисный контур проекта

> **Это опциональный режим проекта.** Он становится обязанностью только после
> строки `сервисный контур kb-architect: принят` в канонических правилах проекта.
> Контракт базы от этого не расширяется: контур обслуживает доставку, применение,
> обратную связь и сигнал о цене структуры.

Сервисный контур нужен, чтобы владелец не помнил четыре разные команды и не был
единственным датчиком поломки. Цикл выполняется при каждом **новом task/session**,
не при каждом сообщении владельца. Проект отвечает на четыре вопроса:

1. установлена ли свежая доступная редакция скилла;
2. применены ли её обязанности и приняты ли решения по новым возможностям;
3. наступил ли триггер детального отчёта;
4. не стала ли структура источником повторяющейся цены.

## Объявление в правилах проекта

```markdown
сервисный контур kb-architect: принят
обновление скилла: автоматически
канал обновления скилла: GitHub public https://github.com/sugestr/kb-architect
маршрут отчётов: <local-inbox | github-issue>
инбокс отчётов: <для local-inbox — прямой приватный путь>
Отчёты о дефектах скилла: детальные, автоматически по триггерам
```

Стабильный канал проекта — только PUBLIC GitHub. Приватная лаборатория является
источником разработки и выпуска, но не каналом установки в рабочие проекты: симлинк на неё
может молча открыть незавершённую редакцию. Рабочая установка — управляемая копия
очищенного публичного выпуска. `--source` остаётся только для теста и maintainer-
workflow, не для проектных правил.

Среда без файловой установки — браузерный скилл, Cowork, чужая машина — не может
выполнить обновление из этого пути. Это не повод писать «автоматически»: сессия
называет точный пакет и исполнителя, а проект остаётся на прежней редакции до
подтверждённой загрузки.

Codex Cloud получает канонические правила проекта из Git, прежде всего через
`AGENTS.md`; локальная user-level установка скилла и local MCP туда не переносятся.
Поэтому облачная готовность проверяется отдельно при создании/обновлении environment:
repo-relative boot canon, recoverable project skills и `kb_environments.py` для
объявленных connector capabilities. Этот gate не добавляется к каждому warm turn и
не задерживает обычный ответ после уже принятой cloud-сессии.

## Исполняемая связность канона

Если проект строит из знания отчёт, prompt, маршрут или программное решение,
запись в Markdown ещё не доказывает, что runtime её применяет. Для повторяемой
классификации или списка (зоны, роли, жанры, обязательные источники) назначь один
логический registry/source; остальные представления должны строиться из него, а не
редактироваться параллельно.

Связность доказывает проектный integration/acceptance test на реальной цепочке:
канонический источник → composition/consumer → итоговый renderer или runtime.
Квитанция «подключено» называет эти три точки и команду проверки. Универсальный
сканер не должен угадывать семантику произвольного Markdown и кода: пока проект не
объявил машиночитаемый граф, такой скан даст либо шум, либо ложный PASS. Поэтому
конкретная проводка и её тест принадлежат проекту; `kb_check.py` проверяет только
общие механические инварианты базы.

## Входной цикл

### Короткая команда владельца

**«Обнови скилл базы знаний»** — action-first: доставить stable, проверить project
delta и сразу продолжить обратимые candidate changes, tests и точечные local commits. Валидные
snapshot/ledger/results переиспользуй по commit/hash. Preflight и diff — evidence, не
остановка для нового «сделай»; длинный protocol prompt владельцу не нужен.

Остановись перед новым предметным выбором, post-results acceptance,
Passwords/Keychain или private runtime, необратимым внешним действием и
push/publication. Явные `проверь`, `аудит`, `read-only`, `только отчёт` запрещают запись.

### 1. Доставить редакцию

Локальная файловая установка по умолчанию проверяет stable update; проект может
явно выбрать `обновление скилла: по сигналу`. Новая task/session сначала читает
короткие правила проекта и **до current state, project-derived вывода и остальных
project tools** один раз запускает:

```bash
python3 <установленный-скилл>/scripts/kb_update.py \
  --public --fast --сделать --project <корень-проекта>
```

Рабочие инструкции берутся из уже установленного локального `SKILL.md`;
агент не открывает public README/SKILL вручную и не клонирует репозиторий, чтобы понять, как
работать. Public используется только как канал freshness/delivery. При валидной
квитанции и parity новый локальный task делает один дешёвый `git ls-remote`. Если HEAD
совпал, clone, повторное чтение контента и тесты не нужны. Изменение HEAD, дрейф или
недостаточная квитанция сразу запускают
полный gate: чистый временный `main`, приёмочные тесты, staging на том же диске,
backup, замена и повторные тесты. Ошибка сети или записи cache называется `UNKNOWN`,
не `CURRENT`/PASS. Совместимая опция `--ttl-hours` больше не отменяет remote probe.

`--project` сразу запускает `kb_apply.py` из той же проверенной редакции: код 0 означает,
что marker актуален **и для v6+ подтверждён tracked release receipt**;
код 1 (`NEEDS_APPLICATION` или `APPLICATION_UNPROVEN`) — что дельта либо
доказательство её применения не закрыты. В action-first режиме это
`SESSION_ACTION=APPLY_PROJECT_DELTA_NOW`, а не конечный отчёт: агент продолжает по
`references/migration.md` до настоящего owner gate. Сам скрипт не принимает
предметные решения за владельца.

По умолчанию цель — installed stable. Явный более ранний `to_version` не расширяй:
проверь его через `kb_apply.py <root> --target-version <to_version>`; детали — в
`references/migration.md`.

Совпавшие HEAD + receipt + fingerprint делают этот gate дешёвым. Внутри той же живой
задачи не запускай этот цикл снова, если root и receipt не изменились. `CURRENT`
разрешает обычный вход. `INSTALLED` требует прочитать установленный `SKILL.md` и
только нужный текущей задаче изменившийся маршрут до предметной работы. `UNKNOWN`
называется владельцу; работа может продолжиться на явно названной установленной
версии, если сама задача не зависит от исправления/возможности нового выпуска.

Если существующая установка — симлинк, полный gate сохраняет его в backup и ставит
обычную управляемую копию публичного выпуска. Недоступная установка называется вслух.

Загруженная инструкция не исчезает из prompt. Поэтому уже длинная task не
прерывается посреди операции только из-за нового HEAD: на первой безопасной границе
она завершает atomic step, запускает update, читает новый entry и изменившийся
route, затем продолжает. Если новый выпуск меняет несовместимый contract/authority
gate, `kb_apply.py` оставляет `NEEDS_APPLICATION`, и продолжение переносится в новую
task после решения владельца. Нельзя писать, что старая инструкция «забыта».

### 2. Применить редакцию к проекту

Доставка и применение — разные операции, но штатная команда выше проверяет их
одним циклом. Для отдельной диагностики или старого проекта выполнить:

```bash
python3 <установленный-скилл>/scripts/kb_apply.py <корень-проекта>
```

Вывод содержит два класса:

- `⟦Д: …⟧` — обязательное дело, потому что прежнее соглашение проекта теперь
  неверно или неполно;
- `⟦В: …⟧` — новая возможность, которой нужен исход владельца: `принято`,
  `отклонено` или `отложено`.

Если код ненулевой, продолжить по `references/migration.md`: **до первой записи**
сохранить exact source commit/hash и открыть release-wide ledger; применить candidate;
показать владельцу diff, tests, `PASS/FAIL/UNKNOWN`, cost и rollback. Tracked-only
rollback — pre-change Git commit без второй копии; внешнее состояние проходит staged cutover. Только после
post-results acceptance финализировать tracked `KB_RELEASE_APPLICATION.json` и поднять
`kb_standard_version`. Просто заменить номер значит скрыть неприменённое обновление;
начальное разрешение на миграцию не является приёмкой результата.

### 3. Проверить текущее состояние

Запустить принятые проектом проверки. Их зелёный исход ограничен тем, что они
перечислили в строке «Проверено». Ошибка запуска и ненайденный вход — не PASS.

Если проект не принимал диагностику при входе, сервисный контур не добавляет её
молча: сначала предлагает владельцу стоимость и ожидаемую пользу. Доставка скилла
не является разрешением менять соглашения базы.

### 4. Закрыть цикл обратной связи

Триггеры живут в одном месте — `assets/templates/defect-report.md`, раздел «Когда
отчёт пора собирать». Проект, объявивший `автоматически по триггерам`, уже получил
разрешение владельца на сборку. Доставку выполняет один маршрутизатор:

```bash
python3 <skill>/scripts/kb_report.py --project <root> --report <file> --do
```

Объявленный local inbox остаётся получателем даже если текущий runtime не может в него
писать: исход `BLOCKED_LOCAL` и **никакого** GitHub fallback. Только проект с явно
удалённым маршрутом может отправить обезличенный GitHub issue, и команда требует
отдельный `--public-safe`. `PREPARED` не является `DELIVERED`.
В linked worktree local auto-route восстанавливает sibling private lab через Git
common-dir; временный runtime-каталог не превращает локальный проект во внешний beta.

Если доставка недоступна, отчёт остаётся файлом проекта, а маршрутизатор печатает
точный target. Дополнение передаётся `--amends <id|filename>`, замена —
`--supersedes <id|filename>`: исходные bytes неизменны, связи живут в
`REPORT_INDEX.json`. Пересказ в чат не заменяет документ. Private-разрешение не делает
отчёт публичным.

Доставка не означает принятие. Лаборатория проверяет каждое наблюдение и даёт ему
исход: выпущено; очередь с условиями; не класс стандарта с владельцем.

## Сигнал «структура стала дорогой»

Сервисный контур не перестраивает базу сам. Он обязан предложить диагностику, если
наступил хотя бы один наблюдаемый сигнал:

1. один механизм дал вторую запись «сломалось»;
2. сессия дважды сказала «этого нет», хотя факт находился в базе;
3. один класс текущего состояния поддерживается в двух местах и уже разошёлся;
4. дорогая операция повторилась, потому что результат некуда положить;
5. база выросла вдвое от последней диагностики или появился новый класс данных;
6. правила регулярно обходят, потому что соблюдение дороже нарушения;
7. владелец сам говорит, что организация мешает работе.
8. точные дубли, временные или производные файлы регулярно попадают в поиск как
   конкурирующий канон либо активное поле растёт без нового класса знания.
9. `kb_cost.py --check` напечатал `OPTIMIZATION_REQUIRED`, evidence lookup потребовал
   уточнить слишком широкий запрос, либо неизменный reference прочитан повторно в
   одной логической задаче.

Сигнал формулируется не как «папки некрасивые», а так:

```text
СТРУКТУРНЫЙ СИГНАЛ
наблюдение: <два случая, пути и даты>
цена: <время / ложный вывод / повторная операция>
гипотеза: <какой класс состояния или маршрут разорван>
предлагаю: сначала read-only диагностику; структуру пока не меняю
```

Случай, где перестройку предложил владелец раньше скилла, записывается как
**owner-initiated**, а не как успех сигнала. После принятия сервисного контура
следующий аналогичный случай проверяет, возникает ли сигнал без напоминания.

## Процедура после сигнала

1. Выполнить read-only часть `references/adopt-existing.md`: профиль проекта,
   источник правды, вход, каналы записи, дубли текущего состояния, цена поиска.
2. Показать владельцу: что оставить; что переносится; какие ссылки и автоматизации
   затронуты; backup; критерии приёмки; откат.
3. Получить отдельное «перестрой» или эквивалентное согласие. Сам сигнал разрешает
   диагностику, но не реорганизацию.
4. Выполнить часть 2 той же процедуры: backup-ветка и тег, поэтапные изменения,
   контрольные вопросы и штатные тесты.
5. В журнале записать отдельно: что было owner-initiated, что нашёл сервисный
   сигнал и что реально стало дешевле после перестройки.

Если сигнал относится не к структуре, а к накопившимся дублям/артефактам, вместо
перестройки предложить read-only инвентаризацию из
`references/garbage-collection.md`. Она не разрешает удаление автоматически.

## Что контур не обещает

- Фоновый daemon и гарантированную доставку без запущенной сессии.
- Hot reload инструкции текущей сессии.
- Автоматическую перестройку структуры.
- Автоматическое принятие новых возможностей выпуска.
- Обновление среды, к которой нет файлового или штатного установочного доступа.

Честная модель: сервисный цикл запускается при входе агентом, а не существует вне
сессии. Если позже среда даст надёжный hook открытия проекта, тот же цикл можно
подключить к нему без изменения семантики.

## Двухслойный вход проекта

Большой файл правил, автоматически загружаемый каждой сессией, сам становится налогом
на простой вопрос. Рекомендуемый вход состоит из двух слоёв:

1. **Короткий boot canon** под `AGENTS.md` и `CLAUDE.md` (лучше два symlink на одни
   байты): назначение проекта; переносимый repo-relative root (обычно `.`); указатель
   текущего состояния; authority и
   внешние/необратимые stop-gates; принятые дешёвые проверки; указатели на
   `PROJECT_ROLES.json` и `KNOWLEDGE_INDEX.json`; `kb_standard_version` и ссылка на подробные
   правила.
2. **Подробные правила по требованию:** структура и владение, recovery, история
   решений, optional modules, длинные процедуры. Они читаются только по trigger.

Разделение не должно прятать authority или stop-condition во втором слое: всё, что
может сделать простой ответ опасным, остаётся в boot canon. Исторический проект не
переписывается массово из-за выпуска; при следующем содержательном изменении входа
сначала измеряют его цену и выносят только статические объяснения.

Абсолютный путь локального canonical checkout нужен при move/acceptance, но не является
активной общей инструкцией проекта: в облачном clone он заведомо иной. Его фиксируют как
датированное evidence приёмки или проверяют через `pwd -P` и
`git rev-parse --show-toplevel`. В shared boot canon используют `project root: .` либо
эквивалентный repo-relative locator.
