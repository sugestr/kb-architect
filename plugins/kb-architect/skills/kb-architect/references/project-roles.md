# Проектные роли

Роль определяет цель и способ работы со знаниями. Инфраструктурная проверка
показывает обнаружение, версии и восстановимость; предметную корректность
принимает ответственный за качество метода (quality owner). Роль не подтверждает
профессиональную лицензию.

## `selection` — выбор метода

Проект объявляет положение ролей (role posture): `required`, `transitioning`
или `not-applicable` с причиной. Состав профессиональных ролей выбирает владелец
проекта либо явно уполномоченный им исполнитель; поручение создать базу такого
выбора не делает. При переходе можно выполнять покрытую и
независимую работу; непокрытый существенный вывод останавливается по ядру.
Отсутствующий реестр сам по себе не означает `not-applicable`.

`PROJECT_ROLES.json` хранит назначение, условия выбора (`load_when`), адрес метода
(`skill`), маршруты знания и необязательный `extends`. Метод находится в одном
`SKILL.md`. Факты, нормы, переписка, диагнозы, планы и рецепты внешних систем
остаются в индексированной базе. Воспроизводимые операции исполняет инструмент;
такой процедурный skill не обязан объявляться профессиональной ролью.

`kb_skills.py <root> --select <id>` строит порядок предков и выбранных ролей.
Общие методы и маршруты читаются один раз. Скрипт разрешает идентификаторы,
но релевантность задачи определяет агент. Неизвестный предок и цикл — ошибки.
`extends` наследует цель, метод и ограничения, но не соседние роли. Ослабление
условия остановки требует изменения владеющего метода и приёмки. Координатор
не получает компетенцию специалиста через организационную иерархию.

Разные условия выбора могут вести к одному методу при общих полномочиях,
источниках, ограничениях и владельце качества. Новый метод или специализация
нужны, если реальные устойчивые задачи требуют другой цели, лестницы источников
или ответственности, либо общий вход постоянно загружает лишнее. Один серьёзный
пробел достаточен; опасную ошибку не надо повторять. Сначала проверь существующую
роль и её условия выбора. Папка, человек, объём и разовый вопрос сами по себе
новой роли не требуют. Слабый сигнал сохраняй с условием возврата без пустого skill.

Проверяй роль по поведению: как её цель изменила сравнение вариантов, какие
источники дали основание и что осталось недоказанным. Проверенное основание
переиспользуют в пределах применимости; роль не требует заново исследовать
каждую мелочь. Объект, период и юрисдикцию задают источники, а не имя роли.

## `location` — канон и восстановление

Место метода определяется областью действия, а не именем агента. Для одного
проекта это отслеживаемый Git метод внутри проекта. Для нескольких — один
репозиторий-владелец, точная закреплённая ревизия (pin) и рецепт восстановления;
потребители объявляют зависимость и собственные маршруты знания.
`.agents/skills/` и `.claude/skills/` служат обнаружению того же канона.
Отдельные копии для Claude и Codex и единственная пользовательская установка
вместо проектного восстановления не допускаются.

Обязательный недоступный метод блокирует только зависящую предметную работу.
Среды исполнения и секреты проверяются отдельно по `modules.md`. Заимствование
сохраняет происхождение и лицензию; изменение общего метода возвращают владельцу.
Перед удалением факта из метода создай адрес в базе и докажи, что роль его находит.

## `role_acceptance` — проверка роли

Начни с `kb_skills.py <root> --prepare-candidate`. Это подготовка без записи:
скрипт показывает заполненные из доступных данных поля и `UNRESOLVED`. У уже
принятого проекта `action: none` не требует нового кандидата.

Новая приёмка хранится в `PROJECT_ROLES.json` как `kb-role-acceptance/v3`.
Читаемые старые схемы 2–5, compact v1/v2 и runner v1 не переписывают ради
формата. До переключения прежний реестр остаётся каноном; кандидата проверяют
через `--registry`. После переключения `.kb-skills.json` оставляют только
указателем совместимости. Порядок проектной приёмки и marker — в `migration.md`.

Разделяй четыре результата: структурную готовность и восстановление, один узкий
проектный validator, работу из свежего контекста и решение по показанному результату.
`--execute-project-check` запускают из `PENDING`. Проверь связанные скриптом
отслеживаемые входы, хеши и бюджет; чужие несовпадающие хеши не затирай.
После изменения входов верни проверку в `PENDING` и повтори затронутый запуск.
Статус перехода допускает тест, но не приёмку. Скрипт не принимает результат
от имени владельца и не доказывает живую работу роли.

Свежая проверка — отдельная сессия без истории изменения, ожидаемого ответа,
имени роли и подсказки ограничения. Дай обычный вопрос и исходные материалы.
По ответу и следу чтения оцени выбор роли, найденное знание и реальное условие
остановки или конфликт. Сохрани точный native run id и `observed_at`.
Вопрос в той же сессии — самопроверка; форма квитанции изоляцию не доказывает.

`TESTED` назначается по наблюдённому запуску. Другая система может получить
`INHERITED` только при тех же канонических байтах, неизменных связях и конфигурации
и уже доказанной способности её среды. Иначе нужен тест или `UNKNOWN`.
Изменение метода или входа требует относящейся проверки; обычный patch и смена
статуса owner/live сами по себе не требуют нового обращения к модели.

Приёмка связывает SHA-256 метода; остальные байты и откат сохраняет Git.
Конкурирующая активная копия блокирует приёмку, выведенная из активных путей — нет.
Дополнительные `kb_behavior.py`, mutation tests и проверки каждой среды нужны
при найденном риске. Полный набор тестов самого скилла выполняют при его выпуске.

`quality` называет владельца, профессиональное ревью, границу между методом
и знаниями и её причину. Отложенная проверка имеет условие возврата и безопасный
режим. Проверка упаковки не даёт профессионального `PASS`. Отдельный файл
качества нужен только его потребителю; внешний обзор не повторяется после каждой
правки без нового основания.

## `cost` — стоимость роли

Измеряй выбранные методы, вспомогательные файлы, адресованные знания и реестры.
`accepted_end_to_end_bytes` — принятый проектом бюджет с областью, единицами,
обоснованием и запасом. Сценарий всех ролей (`all_roles_scenario`) обязателен
как верхняя оценка, но не является ценой каждого вопроса. Порог 8 КиБ в
проверяющей программе — повод для ревью, а не требование потерять нужный метод.

Физические совпадения, предки и пересекающиеся разделы считаются один раз;
раздел включает подразделы до следующего заголовка того же или старшего уровня.
Для запроса измеряется рецепт, результат БД и внешний проект — отдельно.
`COST_SCOPE_PARTIAL` означает неучтённые условные зависимости: объяви нужные
`route_files` либо сохрани ограничение оценки. При `OPTIMIZATION_REQUIRED`
проверь выбор и дубли, затем смысловое разделение или обоснованную смену бюджета.
Потеря найденного знания, полномочий или условий остановки недопустима.
Фактические токены берут из квитанции провайдера либо оставляют `UNKNOWN`.
