# Существующий проект: присоединить контракт или перестроить базу

> **Это справка, не обязательство.** Применение чего-либо отсюда сверх контракта фиксируется в блоке «Соответствие» файла правил проекта — не делается молча. Если ты сессия и попал сюда по релевантности запроса: прочитанное здесь **не становится нормой** оттого, что ты это прочитал.
>
> Формулировки здесь **описательные, а не предписывающие**: «обычно», «разумно», «окупается там, где». Встретишь категоричную — читай её как сильную рекомендацию для описанного случая, а не как правило проекта.

Здесь две разные процедуры, и путать их дорого:

| | Присоединение | Перестройка |
|---|---|---|
| Сколько | 30–90 минут | отдельный проект на часы |
| Что трогает | ничего из существующего | структуру, имена, размещение |
| Когда | **по умолчанию** | только по явной просьбе владельца и при наблюдаемых поломках |
| Бэкап | обычный коммит | **обязательная отдельная ветка-снимок** |

Раньше обе назывались одинаково, и сессия могла превратить осторожное присоединение в миграцию. Если владелец не сказал «перестраивай» — делается присоединение.

**Умирает, когда:** перестройка перестанет требоваться ни одному проекту — тогда остаётся только присоединение, и файл сокращается вдвое.

---

# Часть 1. Присоединение контракта

Базовый случай. **Структура не трогается**: папки, имена файлов, сложившиеся привычки остаются как есть. Переименования ломают ссылки в отправленных документах, пути, на которые смотрит код, и память владельца о том, где что лежит, — а взамен не дают ничего.

## Четыре действия

**1. Вход** — место, где видно текущее состояние без исторических накоплений.

Если в проекте «что дальше» уже вычисляется — из реестра обязательств, календаря, генератора — входом становится эта сборка, и отдельный файл заводить незачем: достаточно описать её в правилах проекта. Иначе `NOW.md` по образцу из контракта, собранный из того, что уже есть в проекте.

Здесь же обычно вскрывается типовая находка: **несколько конкурирующих списков «что дальше»**, датированных разными месяцами. Правильный ход — показать их владельцу и спросить, какой актуален. Угадывание здесь дороже вопроса.

**2. Канал правок** — `CORRECTIONS.md`, пустой, с шапкой из шаблона. Единственный вход для любых плохих новостей, с пометкой вида в начале строки.

**3. Поля** — только там, где условие выполняется, пустых заводить не стоит:

- `verify` — есть утверждение о совершённом действии и есть чем его перепроверить;
- `valid_until` — файл утверждает про настоящее и у утверждения есть предметный срок;
- `generated_from` — файл пишет генератор.

Массовая простановка полей по всем файлам — уже не присоединение, а перестройка. Поле имеет смысл там, где его будет поддерживать штатный писатель этого файла.

**4. Контрольные вопросы** — четыре-шесть тех, что владелец реально задаёт, один с риском ложной уверенности. Прогон с чистого контекста, запись того, где база соврала уверенно.

Плюс журнал эксплуатации с двумя колонками и блок «Соответствие» в правилах проекта: что взято, что отклонено и почему.

## Чего на этом этапе лучше не делать

Не заводить каркас папок, если в проекте уже есть свой. Не включать линтер обязательным шагом. Не брать ничего из справочника, пока в журнале не появится повтор.

## Что владелец говорит

Одну фразу. Четыре действия перечислять не нужно — они здесь.

```
Присоедини контракт kb-architect к этому проекту. Присоединение,
не перестройка: структуру не трогай.
```

Слова «присоединение, не перестройка» — единственное, что стоит сказать явно, потому что это выбор между двумя процедурами, и его делает владелец, а не сессия.

**Признак, что процедура не сработала:** сессия начала переименовывать файлы или двигать папки. Это перестройка, о которой не просили.

# Часть 2. Перестройка базы

Только по явной просьбе. Признак, что она нужна, — **наблюдаемые поломки**: сессии регулярно не находят нужное, знание дублируется и расходится, входов несколько и они противоречат друг другу. «Привести к стандарту» — не признак.

## Шаг 0. Бэкап до всего остального

До первой правки, без исключений:

```bash
git status                 # рабочее дерево должно быть чистым
git add -A && git commit -m "снимок до перестройки базы"
git branch backup/pre-kb-<дата>
git push origin backup/pre-kb-<дата>
git tag pre-kb-<дата> && git push origin --tags
```

Если репозитория нет — он заводится сейчас, до перестройки, а не после.

Если в дереве висят незакоммиченные правки и неотслеживаемые пути, **точка возврата фиктивна**: сначала разобрать их, потом снимок. Это самая частая причина, по которой откат оказывается невозможен.

Ветка и тег остаются навсегда: место они не занимают, а вернуться к состоянию «до» можно одной командой.

## Шаг 1. Опись без изменений

Таблица во временном файле, не в репозитории:

| Файл | КБ | Класс | Дата правки по git | Кто ссылается | Дубликат чего |

Дату брать из git, а не из файловой системы: mtime врёт после клонирования.

Параллельно полезно ответить на пять вопросов:

- **что здесь источник правды** — обычно один-два файла, к которым все обращаются; их ломать нельзя;
- **что дублируется** — одна сводка в нескольких местах, типовая находка;
- **что мертво** — не обновлялось месяцами и ни на что не влияет;
- **какие неявные конвенции уже действуют** — формат дат, порядок разделов, «этот файл не трогать»;
- **какие имена читает код** — генератор, скрипт, скилл, уже отправленный наружу документ. Эти имена неприкосновенны; список составляется до всякого планирования.

## Шаг 2. План — показать владельцу до изменений

Что переезжает и куда · что удаляется, отдельным коротким списком с обоснованием по каждому пункту · что остаётся как есть и почему · сколько файлов затронуто и сколько это часов.

Явное «да» до начала. Реорганизация необратима по восприятию: владелец помнит, где что лежало, и следующий месяц будет искать по старой карте.

## Шаг 3. Порядок изменений

Каждый шаг — отдельный коммит, чтобы откат был возможен не только целиком:

1. паспорт в существующие файлы, **без перемещений** — уже даёт пользу и ничего не ломает;
2. вход: историю вычистить, конкурирующие списки свести к одному;
3. дедупликация — канон и ссылки на него, а не слияние в один большой файл: слитый никто не читает целиком;
4. переезды и переименования, если нужны, — одной пачкой через `git mv`, потом починка ссылок. Имена из списка «читает код» не трогаются;
5. заморозка закрытых периодов и архив;
6. файл правил — последним: к этому моменту видно, какие правила действуют, а какие были декларацией.

## Шаг 4. Проверка и откат

Перестройка удалась, когда новая сессия с чистого контекста решает типовую задачу проекта, не роясь по папкам. Проверяется буквально, на контрольных вопросах.

Что-то пошло не так — возврат одной командой:

```bash
git checkout backup/pre-kb-<дата>     # посмотреть, как было
git revert <коммит>                   # отменить конкретный шаг
git reset --hard pre-kb-<дата>        # вернуть всё (осторожно)
```

## Когда перестройку лучше отложить

Идут активные сроки с последствиями · по базе ежедневно ходят другие сессии или скрипты · рабочее дерево не приведено в порядок и точка возврата фиктивна.

## Что владелец говорит

```
Перестрой базу знаний этого проекта под контракт kb-architect.
Да, я понимаю, что это перестройка, а не присоединение.
Бэкап и план на утверждение — обязательно.
```

Вторая строка нужна: без неё сессия по умолчанию делает присоединение, и правильно делает. Третья — не инструкция, а страховка: если сессия начнёт двигать файлы, не показав ни ветки-снимка, ни плана, владелец видит это сразу и останавливает.

**Признак, что процедура не сработала:** первый коммит с перемещениями появился раньше, чем ветка `backup/pre-kb-<дата>` и явное «да» на план.
