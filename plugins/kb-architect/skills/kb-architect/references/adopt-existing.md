# Существующий проект: присоединить контракт или перестроить базу

> **Это справка, не обязательство.** Применение чего-либо отсюда сверх контракта фиксируется в блоке «Соответствие» файла правил проекта — не делается молча. Если ты сессия и попал сюда по релевантности запроса: прочитанное здесь **не становится нормой** оттого, что ты это прочитал.
>
> Формулировки здесь **описательные, а не предписывающие**: «обычно», «разумно», «окупается там, где». Встретишь категоричную — читай её как сильную рекомендацию для описанного случая, а не как правило проекта.

Здесь две разные процедуры, и путать их дорого:

| | Присоединение | Перестройка |
|---|---|---|
| Сколько | 30–90 минут | отдельный проект на часы |
| Что трогает | ничего из существующего | структуру, имена, размещение |
| Когда | **по умолчанию** | только по явной просьбе владельца и при наблюдаемых поломках |
| Бэкап | обычный коммит | **обязательная отдельная ветка-снимок** |

Раньше обе назывались одинаково, и сессия могла превратить осторожное присоединение в миграцию. Если владелец не сказал «перестраивай» — делается присоединение.

**Умирает, когда:** перестройка перестанет требоваться ни одному проекту — тогда остаётся только присоединение, и файл сокращается вдвое.

---

# Часть 1. Присоединение контракта

Базовый случай. **Структура не трогается**: папки, имена файлов, сложившиеся привычки остаются как есть. Переименования могут сломать активные пути кода, генераторов и интеграций, а также память владельца о том, где что лежит; в режиме присоединения эта цена не окупается. Уже выданный неизменяемый документ — исторический снимок, а не автоматически активный потребитель внутреннего пути: это различие становится существенным только при явно разрешённой перестройке ниже.

## Четыре действия

**1. Вход** — один физический owner правил и текущего состояния без исторических
накоплений. Обычный вариант — раздел «Сейчас» в уже автоматически читаемом
`CLAUDE.md`/`AGENTS.md` (два имени могут быть symlink на одни байты).

Если в проекте «что дальше» уже вычисляется — из реестра обязательств, календаря,
генератора — входом становится эта сборка, и отдельный файл заводить незачем:
достаточно описать её в правилах проекта. Иначе текущее состояние остаётся разделом
того же boot-файла.

Отдельный `NOW.md` оправдан, когда состояние меняется заметно чаще стабильных правил
или его независимо собирает генератор. Это допустимая оптимизация, не требование
стандарта: без такой причины второй файл только создаёт второй маршрут и риск
расхождения.

Здесь же обычно вскрывается типовая находка: **несколько конкурирующих списков «что дальше»**, датированных разными месяцами. Правильный ход — показать их владельцу и спросить, какой актуален. Угадывание здесь дороже вопроса.

**2. Канал правок** — `CORRECTIONS.md`, пустой, с шапкой из шаблона. Единственный вход для любых плохих новостей, с пометкой вида в начале строки.

**3. Поля** — только там, где условие выполняется, пустых заводить не стоит:

- `verify` — есть утверждение о совершённом действии и есть чем его перепроверить;
- `valid_until` — файл утверждает про настоящее и у утверждения есть предметный срок;
- `generated_from` — файл пишет генератор.

Массовая простановка полей по всем файлам — уже не присоединение, а перестройка. Поле имеет смысл там, где его будет поддерживать штатный писатель этого файла.

**4. Контрольные вопросы** — четыре-шесть тех, что владелец реально задаёт, один с риском ложной уверенности. Прогон с чистого контекста, запись того, где база соврала уверенно.

**Вход измеряется, но не обрезается по универсальному числу.** `kb_check.py` бесплатно
показывает rules, current и дедуплицированный статический bootstrap:

```bash
python3 <путь к скиллу>/scripts/kb_check.py <корень>
```

Байты полезны как proxy цены доставки, но не отвечают, уникален ли текст и сохранится
ли нужное поведение после выноса. Поэтому без явного `project_boot_budget_bytes`
число информационное. Если проект принимает такой общий бюджет, checker делает красным
только его превышение. Лимит по строкам не вводится: в плотном markdown строка не
единица объёма.

Плюс журнал эксплуатации с двумя колонками и блок «Соответствие» в правилах проекта: что взято, что отклонено и почему.

**Объяви, где у проекта вход, журнал и вопросы.** Контракт требует инвариант, а не файл, и проекты этой свободой пользуются: вход в подпапке, журнал разделом внутри другого документа. Инструменты ищут по известным именам и по объявлению — второе надёжнее. Строки идут в блок «Соответствие» (шапка входа тоже читается):

```
kb_standard_version: <номер из шапки SKILL.md>
вход: claude/STATUS.md
журнал: раздел «Журнал эксплуатации» в docs/KB.md
контрольные вопросы: docs/QUESTIONS.md
```

Редакция — **числом**. Наблюдение с проекта: поле заполнили фразой «редакция от 02.08.2026 (три поля, четыре правила…)» — человеку понятно, сравнить нельзя. Поле, которое нельзя сравнить, не отличается от незаполненного.

**Последний шаг присоединения — прогон, а не запись.**

```bash
python3 <путь к скиллу>/scripts/kb_due.py <корень>
python3 <путь к скиллу>/scripts/kb_check.py <корень>
```

Смотреть надо не только на находки, но и на строку «Проверено:» и на раздел «в порядке»: там должны быть названы **те самые** пути, которые ты только что объявил. Не названы — объявление до инструментов не дошло, и все последующие «чисто» будут означать «не искали». Присоединение, которое не проверили прогоном, — это запись о присоединении.

**5. Записка владельцу** — обязательный последний шаг. Он не читал ни контракта, ни справочника, и не должен: скажи обычными словами, что появилось, что от него нужно (почти ничего) и что сессия будет делать сама. Если от чего-то осознанно отказались — одной строкой, чтобы следующая сессия не «доводила до стандарта». Образец — `assets/templates/first-run.md`.

## Чего на этом этапе лучше не делать

Не заводить каркас папок, если в проекте уже есть свой. Не включать проверку обязательным шагом. Не брать ничего из справочника, пока в журнале не появится повтор.

## Что владелец говорит

Одну фразу. Четыре действия перечислять не нужно — они здесь.

```
Присоедини контракт kb-architect к этому проекту. Присоединение,
не перестройка: структуру не трогай.
```

Слова «присоединение, не перестройка» — единственное, что стоит сказать явно, потому что это выбор между двумя процедурами, и его делает владелец, а не сессия.

**Признак, что процедура не сработала:** сессия начала переименовывать файлы или двигать папки. Это перестройка, о которой не просили.

# Часть 1а. Диагноз без изменений

Между «ничего не трогаем» и «перестраиваем всё» есть случай, который встречается чаще обоих: **система хранения так себе, но не сломана.** Что-то находится плохо, что-то дублируется, где-то две правды — но сроки не горят и катастрофы нет. Полная перестройка тут дороже пользы, а делать вид, что всё в порядке, — глупо.

Для этого режим третий: **сказать, что плохо, и не трогать.**

Вызывается словами вроде «покажи, что не так с хранением в этом проекте». На выходе — список проблем, отсортированный по цене, а не по заметности. По каждой: что именно не так, **во что это обходится**, как чинится и сколько это стоит. Ни одного изменения в файлах.

## Что искать

Порядок — от дорогого к косметическому. Косметическое ниже черты чинить обычно не надо вовсе.

| Что | Как выглядит | Чем плохо |
|---|---|---|
| **два источника на один вопрос** | два списка «что дальше», два файла с одним сроком, сводка и её копия | сессия выберет произвольно и не скажет, что выбирала |
| **утверждение без доказательства** | «подано», «оплачено», «отправлено» без номера, ссылки или способа перепроверить | через полгода не отличить сделанное от намеченного |
| **снимок без срока годности** | конспект состояния чужой системы с честной датой правки | мёртв, а выглядит свежим: менялся мир, а не файл |
| **вход с историей** | «где мы» разрослось в летопись | текущее состояние приходится вычитывать из хроники |
| **знание только в переписке** | решения и причины живут в чатах, а не в файлах | исчезнет вместе с контекстом, восстановить нельзя |
| **интерпретация выглядит фактом** | вывод, диагноз, гипотеза или мировоззренческий тезис записан рядом с источником без границы и посылок | новый источник опровергает всё сразу; непонятно, что наблюдалось, а что было объяснением |
| **источник не прослеживается** | сводка сообщает утверждение, но от него нельзя дойти до документа, измерения или записи сообщения | проверку приходится повторять с нуля; уверенность шире доказательства |
| **обязательная роль не восстанавливается** | project rules требуют role skill, но он только user-global, не отслеживается Git, имеет битую discovery-ссылку или недоступен одному из поддерживаемых агентов | fresh clone восстанавливает факты, но теряет роль, source ladder и stop conditions; предметный ответ меняется от машины |
| **локальная возможность выдана за переносимую** | правила требуют почту/MCP/Keychain/папку вне Git, но не называют provider, identity, scope и acceptance по средам | cloud/fresh clone либо молча теряет источник, либо работает не с тем аккаунтом; ответ «проверено» становится недоказуемым |
| **имя, которое читает код** | файл, на который смотрит скрипт или отправленный документ | переименование ломает молча |
| — черта — | | |
| несогласованные имена, разный формат дат, файлы не по папкам | | стоит времени только при чтении глазами |

## Как это чинится: по одной, по ходу дела

**Не кампанией.** Список — не план работ на выходные, а порядок, в котором чинить, когда рука и так в этом файле. Правило простое: **открыл файл по делу — почини то, что в списке про него.** Перестройка целиком дороже и почти всегда бросается на середине.

Исключение одно: если наверху списка стоит «два источника на один вопрос», это стоит свести сразу и отдельно. Пока их два, любая сессия может ответить неверно, и никто не заметит.

## Чего диагноз не делает

Не переименовывает, не переносит, не заводит папок, не проставляет полей. Всё это — уже перестройка, часть 2, и требует бэкапа и явного «да».

Для исторической базы дополнительно применим чек-лист ролей знания из
`references/knowledge-roles.md`. Он проверяет происхождение, границу между
наблюдением и интерпретацией, вытеснение и воспроизводимость сводок, но не
предписывает универсальные типы или каталоги.

Определить role posture даже если роли пока не обнаружены: `required`,
`transitioning` или `not-applicable` с причиной. Для required/transitioning
инвентаризировать repo-local, user-global и cross-repo экземпляры; сверить
`PROJECT_ROLES.json`, `KNOWLEDGE_INDEX.json`, физический канон, обе discovery-точки,
границы полномочий, quality owner/review, оба validator, обычные и all-roles costs и
fresh-clone recovery. Для каждого active runtime root сохранить найденные
`id/path/hash/version`; symlink означает только structural state. Accepted
`ROLE_ACCEPTANCE.json` отдельно доказывает structural, unforced fresh-session discovery,
synthetic-first behavior и post-results owner acceptance. Старый
`.kb-skills.json` принимается как legacy до интерактивной миграции. Запустить:

```bash
python3 <путь-к-kb-architect>/scripts/kb_skills.py <корень-проекта>
```

Required global-only role, битая ссылка, конфликт имён/копий, отсутствие agent
coverage, неизвестный knowledge route или нерешённая pinned dependency блокируют предметную готовность.
Непокрытая предметная работа при `transitioning` также блокируется; уже покрытая и
чисто инфраструктурная может продолжаться. Отсутствующий реестр — неизвестная
позиция, не осознанное `not-applicable`. Устойчивый паттерн и поля ролей описаны в
`references/project-roles.md`.

Если проект зависит от внешних connector/MCP или готовится к облачной работе,
отдельно проверить `.kb-environments.json`: Git-tracked `AGENTS.md`/`CLAUDE.md`,
repo-relative активные инструкции, exact runtime/provider/account alias/scope,
authority, safe acceptance и fallback. Не копировать в этот файл глобальный inventory
и секреты. Для требуемой возможности:

```bash
python3 <путь-к-kb-architect>/scripts/kb_environments.py <корень-проекта> \
  --runtime codex-cloud --require <capability.id>
```

Missing registry означает `not evaluated`, а accepted local MCP не доказывает cloud
provider. Этот gate выполняется при adopt/move/cloud acceptance, не на каждый вопрос.

**Умирает, когда:** первая же диагностика в проекте перестанет находить что-либо сверх косметики — тогда режим не нужен, достаточно присоединения.

## Готовый текст

```
Покажи, что не так с хранением в этом проекте. Ничего не меняй.

Список проблем по цене: что не так, во что обходится, как чинится,
сколько стоит. Отдельно отметь, где на один вопрос есть два источника —
это чиню первым.

Файлы не трогай, папки не заводи, ничего не переименовывай.
```

# Часть 2. Перестройка базы

Только по явной просьбе. Признак, что она нужна, — **наблюдаемые поломки**: сессии регулярно не находят нужное, знание дублируется и расходится, входов несколько и они противоречат друг другу. «Привести к стандарту» и размер файла сами по себе — не признаки.

## Шаг 0. Бэкап до всего остального

До первой правки, без исключений:

```bash
git status                 # рабочее дерево должно быть чистым
git add -A && git commit -m "снимок до перестройки базы"   # только если пишущий один
# несколько пишущих — перечисли свои пути: git add путь1 путь2 …
git branch backup/pre-kb-<дата>
git push origin backup/pre-kb-<дата>
git tag pre-kb-<дата> && git push origin --tags
```

Если репозитория нет — он заводится сейчас, до перестройки, а не после.

Если в дереве висят незакоммиченные правки и неотслеживаемые пути, **точка возврата фиктивна**: сначала разобрать их, потом снимок. Это самая частая причина, по которой откат оказывается невозможен.

Ветка и тег остаются навсегда: место они не занимают, а вернуться к состоянию «до» можно одной командой.

## Шаг 1. Назначение и опись без изменений

В опись включить роли отдельно от базы и инструментов: что задаёт поведение, где
единственный канон, обязательность по trigger, knowledge routes, покрытие Claude/Codex,
внешние зависимости и стоимость реальных маршрутов. Не переносить факты и инструкции
внешних систем в роль ради удобства миграции.

До файловой карты назвать **устойчивый объект и назначение проекта**: что он должен
обслуживать через год-два и на какие реальные вопросы владельца отвечать. Если имя или
верхний уровень выросли из первого инцидента, человека либо временной ветки работы, не
принимать эту историческую ось за будущую структуру. Выход — одно предложение о
назначении и список предметных областей, не готовая папочная схема. Для нейтральной
диагностики использовать первый вопрос из `references/00-kak-chitat.md`; для
исторической базы — начало аудита из `references/knowledge-roles.md`.

Этот смысловой гейт вытесняет построение новой карты прямо из старых имён: опись всё
ещё нужна, но теперь описывает материал относительно назначения проекта, а не наоборот.

До решения о дроблении определить форму проекта:

- `focused`: один предмет и общий рабочий цикл; большая глубина, история или число
  доказательств не превращают его в portfolio;
- `portfolio`: несколько областей с общей семейной/корпоративной координацией;
- `hybrid`: общий hub и доменные контуры, из которых только действительно автономные
  получают собственный current/repository/runtime.

Физическую границу проводят при расхождении authority/владельца, доступа и
чувствительности, current/очереди, жизненного цикла, интеграций или recovery. Количество
ролей и байт — диагностические числа, не граница. Для portfolio/hybrid сначала строят
route map и проверяют, что hub не копирует доменные факты.

Таблица во временном файле, не в репозитории. Для boot/current опись идёт до
сокращения и покрывает каждый смысловой блок — иначе невозможно доказать, что ничего
уникального не потеряно:

| Файл/раздел | Блок | Всегда нужен? | Новый адрес/trigger | Кто ссылается | Дубликат чего |

Дату брать из git, а не из файловой системы: mtime врёт после клонирования.

Параллельно полезно ответить на пять вопросов:

- **что здесь источник правды** — обычно один-два файла, к которым все обращаются; их ломать нельзя;
- **что дублируется** — одна сводка в нескольких местах, типовая находка;
- **что мертво** — не обновлялось месяцами и ни на что не влияет;
- **какие неявные конвенции уже действуют** — формат дат, порядок разделов, «этот файл не трогать»;
- **какие имена читают активные потребители** — код, hook, генератор, скрипт,
  интеграция или живой внешний процесс. Их либо сохраняют, либо чинят и проверяют в том
  же миграционном блоке;
- **какие старые имена существуют только в исторических снимках** — уже выданный
  неизменяемый output не переписывают, но он сам по себе не запрещает менять живой
  канон. Если старый адрес важен для аудита, сохраняют provenance или карту переезда.

## Шаг 2. План — показать владельцу до изменений

Что переезжает и куда · что удаляется, отдельным коротким списком с доказательством
дубликата по каждому пункту · что остаётся как есть и почему · сколько файлов
затронуто и сколько это часов · какой обычный fresh-context сценарий докажет recall,
authority и stop-condition после изменения.

Явное «да» до начала. Реорганизация необратима по восприятию: владелец помнит, где что лежало, и следующий месяц будет искать по старой карте.

## Шаг 3. Порядок изменений

Каждый шаг — отдельный коммит, чтобы откат был возможен не только целиком:

1. паспорт в существующие файлы, **без перемещений** — уже даёт пользу и ничего не ломает;
2. выбрать один физический current owner: inline-раздел или отдельный источник;
   конкурирующие списки свести к нему без удаления уникальных строк;
3. дедупликация — канон и ссылки на него, а не слияние в один большой файл: слитый никто не читает целиком;
4. переезды и переименования, если нужны, — одной пачкой через `git mv`, затем починка
   и проверка активных ссылок. Путь активного потребителя не ломают молча: его либо
   сохраняют, либо обновляют в этом же блоке. Исторические снимки не переписывают и не считают автоматическим запретом на изменение живого канона;
5. заморозка закрытых периодов и архив;
6. файл правил — последним: к этому моменту видно, какие правила действуют, а какие
   были декларацией. Каждый вынесенный блок получает точный trigger/address до удаления
   старой копии.

## Шаг 4. Проверка и откат

Перестройка удалась, когда новая сессия с чистого контекста решает типовую задачу
проекта, находит вынесенное знание, соблюдает authority и останавливается хотя бы на
одном реальном stop-condition. Размер и structural checker этого не доказывают.

Что-то пошло не так — возврат одной командой:

```bash
git checkout backup/pre-kb-<дата>     # посмотреть, как было
git revert <коммит>                   # отменить конкретный шаг
git revert <диапазон коммитов>        # отменить блок, сохранив историю
```

## Когда перестройку лучше отложить

Идут активные сроки с последствиями · по базе ежедневно ходят другие сессии или скрипты · рабочее дерево не приведено в порядок и точка возврата фиктивна.

## Что владелец говорит

```
Перестрой базу знаний этого проекта под контракт kb-architect.
Да, я понимаю, что это перестройка, а не присоединение.
Бэкап и план на утверждение — обязательно.
```

Вторая строка нужна: без неё сессия по умолчанию делает присоединение, и правильно делает. Третья — не инструкция, а страховка: если сессия начнёт двигать файлы, не показав ни ветки-снимка, ни плана, владелец видит это сразу и останавливает.

**Признак, что процедура не сработала:** первый коммит с перемещениями появился раньше, чем ветка `backup/pre-kb-<дата>` и явное «да» на план.
