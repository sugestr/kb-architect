# Перенос проекта в общее поле Claude и Codex

> **Это справка, не обязательство для всех проектов.** Она применяется только по
> прямой просьбе владельца перенести конкретный проект. Перенос меняет расположение
> рабочего дерева и правила взаимодействия агентов, поэтому не запускается из
> одной лишь диагностики.

Фразы вида **«перенеси себя в общее поле»**, **«перенеси этот проект в общую
папку Claude и Codex»** означают: провести процедуру ниже для текущего проекта.
Если владелец не назвал другое место, общий корень — `~/Documents/Projects`.

## Что считается результатом

Проект совместим с обеими системами только когда одновременно выполнено всё:

- существует один канонический checkout в общем корне;
- Claude и Codex читают один свод проектных правил без двух ручных копий;
- последовательная запись идёт в этом checkout, параллельная — в отдельных
  временных worktree и ветках;
- активные абсолютные пути, скрипты и интеграции указывают на новое место;
- свежая сессия каждой системы открыла новый путь и прошла приёмку;
- старого редактируемого checkout нет. Временный симлинк на новый путь допустим
  только до завершения переподключения.

Само нахождение каталога в `~/Documents/Projects` не является доказательством.
До двух приёмок состояние называется **«миграция не завершена»**.

## Что разрешает команда владельца

Команда на перенос разрешает: проверить текущий проект; остановить его запись на
время миграции; переместить весь каталог в объявленный общий корень; обновить
активные пути и правила **этого проекта**; создать и затем убрать временный
симлинк старого пути; выполнить проверки и открыть проект штатным механизмом
обеих систем.

Она не разрешает: менять remote или visibility; переписывать Git-историю;
удалять чужие worktree; править другие проекты; редактировать живой конфиг
приложения обходным способом; выбирать новое имя при занятом target. Для этого
нужно отдельное решение владельца.

## 1. Зафиксировать исходное состояние

Все команды выполнять с явным `cwd` или `git -C <точный-путь>`.

1. Получить физический путь (`pwd -P`) и Git-корень. Если текущий путь уже
   находится в общем корне, каталог не двигать — перейти сразу к проверке правил
   и двум приёмкам.
2. Вычислить target как `<общий-корень>/<имя-каталога>`. Если он существует —
   **остановиться**. Не сливать каталоги и не придумывать другое имя.
3. Зафиксировать branch, HEAD, upstream, remotes, `git status --short`, список
   worktree, submodules и вложенные `.git`. Неизвестный nested repo — блокер.
4. Остановить других писателей. Открытая читающая сессия допустима; любой другой
   процесс, который может писать, должен закончить блок или перейти в паузу.
5. Проверить, что дерево чистое. Незакоммиченная работа принадлежит её автору:
   перенос не должен прятать её внутри операции. Если дерево грязное — либо автор
   делает точечный commit, либо перенос останавливается.
   Здесь четыре разные сущности, и ни одна резервная не становится вторым каноном:
   **канонический checkout** — единственное рабочее дерево; **remote-recovery** —
   удалённая Git-история; **bundle** — замороженный файл всех refs на момент переноса;
   **snapshot данных вне Git** — защита ignored/untracked-материала. Bundle и snapshot
   служат проверке и аварийному восстановлению, а не обычной работе; новый checkout или
   второй remote под словом «backup» не создаётся.
6. Создать проверяемый backup вне перемещаемого каталога: для Git — bundle всех
   refs и файл с исходными HEAD/remotes; для данных вне Git — архив или снапшот с
   манифестом. Bundle не содержит untracked-файлы, поэтому чистое дерево проверяется
   отдельно, а не подразумевается из наличия bundle.
7. Найти точный старый абсолютный путь в активных правилах, скриптах,
   автоматизациях и известных конфигурациях приложений. Исторические записи не
   переписывать механически: старый путь в них может быть фактом прошлого.

## 2. Подготовить совместимость до перемещения

### Один свод правил

Найти `AGENTS.md`, `CLAUDE.md` и нейтральный файл правил, если он есть.

- Уже указывают на один файл — сохранить схему.
- Полные правила есть только в одном — считать его каноном и дать второй системе
  симлинк на те же байты.
- Два файла содержательно расходятся — **остановиться и показать diff**. Сливать
  полномочия и запреты по догадке нельзя.
- Новый нейтральный файл (`PROJECT_RULES.md`, `WORKSHOP.md` или существующий
  эквивалент) заводить только если это не ломает принятую архитектуру проекта.

В канонических правилах после согласования должны быть явно видны:

```markdown
## Claude и Codex

канонический checkout: <физический новый путь>
совместимость: Claude + Codex; миграция не завершена до двух приёмок

- Последовательная работа: один checkout, чистое дерево при передаче.
- Параллельная запись: отдельный worktree и ветка на каждого писателя.
- Коммиты: только перечисленные пути; широкое добавление запрещено.
- Вход, канал правок и inbox: <проектные пути>.
```

Это не второй стандарт. Здесь только проектные значения и принятые способы из
`references/collaboration.md`; канон общего паттерна остаётся в скилле.

### Пути

Активные ссылки на старый корень заменить на новый **до остановленного
миграционного commit** либо сразу после `mv`, пока другие сессии не работают.
Относительные пути внутри репозитория предпочесть абсолютным. Межпроектный путь
делать абсолютным только когда получателю действительно нужен внешний каталог.

Проверить также Git hooks, worktree metadata, submodules, LFS, локальные MCP,
планировщики и app-регистрации. Наличие имени системы в старом пути — не ошибка
само по себе; ошибка — когда этот путь участвует в текущей операции и перестанет
разрешаться после удаления временного симлинка.

## 3. Переместить один канон

Для общего корня на том же диске использовать перенос каталога, а не
`copy → проверить когда-нибудь → удалить`: копирование создаёт два редактируемых
канона ровно в момент, когда дисциплина слабее всего.

1. Создать общий корень, если его ещё нет.
2. Ещё раз проверить, что target отсутствует и дерево не изменилось после
   preflight.
3. Переместить **точный** source в **точный** target без glob и без рекурсивного
   удаления.
4. Если текущей сессии или приложению нужен старый путь, создать там временный
   симлинк на target. Это адресный мост, не checkout. В правилах и новых командах
   сразу использовать target.
5. Все дальнейшие Git-команды выполнять как `git -C <target> ...`; не полагаться
   на унаследованный `cwd` перемещённого процесса.

Если перенос оказался межфайловым копированием, операция прекращается до
появления второго рабочего канона: нужен отдельный staging, точное сравнение и
атомарное переключение, согласованное с владельцем.

## 4. Проверить новый checkout

Сразу после переноса доказать:

- физический Git-root равен target;
- HEAD, branch, upstream и remotes совпадают с исходной записью;
- `git status --short` пуст;
- старый путь — отсутствует либо является симлинком именно на target;
- поиск старого абсолютного пути не находит активных зависимостей;
- проектные штатные тесты проходят;
- принятые `kb_check.py` и `kb_due.py` выполняются из target и честно называют
  всё, что не смогли проверить.

Нельзя чинить drift копированием из старого пути: target — единственный канон с
момента успешного `mv`.

## 5. Две независимые приёмки

Текущая сессия не может заверить вторую платформу. Каждая система открывает
target **свежей сессией** и отдельно подтверждает:

1. какой физический путь и Git-root она видит;
2. какой HEAD и remote читает;
3. какой файл является каноном правил и что `AGENTS.md`/`CLAUDE.md` не разошлись;
4. где вход, канал правок и inbox;
5. как работать последовательно и как — параллельно;
6. что штатные проверки запускаются из нового места.

Если система не умеет сама зарегистрировать или открыть новый путь, агент не
пишет «готово»: он даёт владельцу **один точный шаг**, после которого выполняет
свою приёмку. Живой конфиг приложения не редактируется за его спиной.

После обеих приёмок в существующем журнале решения или блоке соответствия
фиксируются: дата; old path; target; HEAD миграции; `Claude: принято`;
`Codex: принято`. Только затем удалить временный симлинк и повторить поиск старого
пути. Проект теперь считается находящимся в общем поле.

## 6. Первый рабочий цикл — часть доказательства

Техническая приёмка доказывает доступ, а не работу правил. Первый реальный цикл
проводится последовательно: одна система делает содержательный блок и точечный
commit, вторая начинает с чистого дерева, читает тот же вход и продолжает либо
останавливается на расхождении.

Первую реальную параллельную запись проводить только отдельными worktree. Любая
потеря состояния, неясное владение, повторное сообщение или зависимость от
старого пути записывается как наблюдение эксплуатации. До этого нельзя говорить,
что новая межагентская схема проверена практикой.

## Откат

До первой записи после переноса откат — обратный перенос того же каталога после
остановки обеих систем; временный симлинк сначала убрать. После появления новых
коммитов переносить назад можно только весь тот же checkout с актуальной
историей — никогда не восстанавливать старую копию поверх него.

Backup нужен для доказательства и аварийного восстановления, а не как второй
рабочий источник. После отката перепроверить HEAD/remotes, активные пути и обе
app-регистрации так же, как при переносе вперёд.

## Что сообщить владельцу

Финальный ответ содержит: old path → target; backup и checksum; HEAD/remotes до
и после; что изменено в правилах и путях; результаты тестов; статус приёмки
Claude и Codex; существует ли временный симлинк; что осталось человеку. Фраза
«папка перенесена» без этой приёмки означает только файловую операцию.
