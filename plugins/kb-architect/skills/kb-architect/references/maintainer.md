# Сопровождение контракта и скилла

Этот reference только для task owner repository `kb-architect`. Consumer task не
становится maintainer по просьбе «для всех»: её route — баг-репорт из `SKILL.md`.
Контракт с версии 6.1 не заморожен, но и не меняется по каждому замечанию.

Прежняя заморозка не получила ретроспективный `PASS`: её session/journal threshold
оказался недоказуем сохранёнными артефактами, а сам инструмент менялся внутри окна.
Владелец явно прекратил старую governance-модель перед 6.1. Старый текст, полная
очередь и исход каждого пункта сохранены в private Git/decision; рабочая сессия не
платит контекстом за этот исторический спор. Новый contract change проходит release
delta, cost/behavior checks, независимый audit и post-results owner acceptance.

## Что является входом

Приоритет имеют воспроизводимые факты эксплуатации: исходный запрос, exact version,
проектный source snapshot, наблюдаемое поведение, проверяемый counterexample, цена и
границы полномочий. Ревью без живого случая может предложить гипотезу, но не доказывает
ни универсальность проблемы, ни работоспособность лекарства.

Проверяй систему целиком: `SKILL.md`, контракт, routed references, templates, scripts,
fixtures, release metadata и фактический output. Зелёный checker доказывает только свой
scope. Если он посмотрел не туда, упал без красного исхода или не исполнил обещанную
проверку, это fail-open.

## Классификация каждого наблюдения

Каждый пункт отчёта получает ровно один исход:

| Исход | Значение |
|---|---|
| `defect` | действующий текст/код противоречит себе, врёт, молчит или не исполняет заявленный gate |
| `enhancement` | полезная новая возможность или обязанность; проблема реальна, решение ещё надо доказать |
| `project-specific` | сбой находится в правилах, данных, роли или wiring одного проекта |
| `rejected` | предложение дублирует существующий механизм, расширяет scope без пользы либо опровергнуто evidence |

Отчёт не закрывается частично. У каждого наблюдения фиксируются решение, evidence,
acceptance и владелец следующего действия. Исходный payload не переписывается:
исправление или уточнение связывается addendum/supersedes receipt.

## Когда менять обязательный контракт

Контракт меняется, если выполнено хотя бы одно:

- один и тот же отказ подтверждён в разных проектах;
- текущий обязательный текст сам создаёт ошибку, дубль или лишнюю постоянную цену;
- правило фактически стало обязательным через template/script, но отсутствует в
  контракте, поэтому реальный объём обязанностей скрыт;
- без общего инварианта проект не может честно отличить `PASS` от `UNKNOWN`;
- узкий gate нужен непосредственно перед необратимым действием и более дешёвой защиты
  нет.

Не добавляй в ядро устройство одного проекта, универсальную онтологию знаний,
профессиональную методику роли, список конкретных tools или точную структуру папок.
Проектное решение остаётся project-specific; повторяемая механика может стать routed
reference/script; только действительно общий инвариант становится контрактом.

Удаление проходит тот же тест, что добавление: какое реальное обязательство исчезает,
кто его потребляет и каким тестом обнаружится потеря. Устаревшие объяснения, история,
закрытые очереди и примеры инцидентов удаляются из runtime package без сожаления — Git
и private decisions уже сохраняют provenance.

## Цена изменения

До реализации назови:

1. какой существующий слой является владельцем правила;
2. что новая формулировка вытесняет, а не дублирует;
3. какие маршруты подорожают или подешевеют;
4. как проверяется recall/authority/stop после оптимизации;
5. какая project migration delta нужна и как откатиться.

Cost baseline — бюджет. Не принимай точное равенство размера изменяемого знания за
готовность: обычная append-only запись тогда превращает сопровождение в постоянную
перепись чисел. Измеряй отдельно entry, static route и actual provider usage. Не
смешивай bytes/оценочные токены с billing receipts.

## Реализация и независимая проверка

- Чини подтверждённый defect узко и добавляй воспроизводящий behavioral regression.
- Enhancement сначала проверяй на реалистичном сценарии; не превращай пример в
  универсальное правило.
- Для сложного изменения используй независимый fresh-context аудит: дай исходный
  запрос, skill и минимальные сырые артефакты, но не подсказывай ожидаемый вывод.
- Разделяй `STRUCTURAL_PASS`, runtime discovery, behavior, owner acceptance и
  профессиональную correctness. Одно не заменяет другое.
- Выпускай связный batch, а не версию на каждую мысль. Новый подтверждённый риск может
  переоткрыть diff; повторное ревью без новой evidence — нет.

`metadata.version` — единственная текущая версия скилла. Отдельный минимальный
уровень проекта отвечает только на вопрос, обязан ли старый проект обновиться:
для `6.3.3` всё ниже `6.3.0` обновляется один раз. Patch выше этого порога
ставится везде, но не открывает повторную project migration.

## Release и authority

Private lab остаётся единственным редактируемым source; public — очищенный stable
snapshot. Local commit, private delivery, public push/release и изменение чужого
проекта имеют раздельную authority. Release считается завершённым только после тестов,
cost gate, portable validator, двух одинаковых builds, allowlist/leakage проверки,
exact public diff, tag/asset push, private receipt и повторной drift-проверки.

После публикации эти проверки не исполняются заново на каждой машине. Установка
принимает exact public commit/archive/fingerprint, создаёт одну управляемую копию,
атомарно переключает стандартные Claude/Codex discovery links и сохраняет предыдущую
копию для отката. Она не запускает и не перезапускает модель, Мегамозг или клиент:
следующая полноценная сессия прочитает новый скилл обычным startup-механизмом.
Install receipt доказывает file parity и единое physical tree; runtime probe нужен
только для диагностики фактического сбоя новой сессии.

Новый минимальный уровень проекта требует pre-change commit, candidate, честные
исходы и решение владельца. Одна короткая квитанция меняет marker; patch её не трогает.
